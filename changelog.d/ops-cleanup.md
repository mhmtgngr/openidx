### Added
- **The box deploy is a script in the repository.** `scripts/box-deploy.sh` is the step-by-step deploy for the single-host reference box (rootless `oidx-*` user units, `oidx-pg` in podman, a bind-mounted console), which had been rewritten in a temp folder for every release: `preflight`, `rehearse` (restores the newest dump into a throwaway `postgres:16-alpine` on a loopback port, with the live cluster's roles, and runs the staged migrations there), `dump`, `stop`, `migrate` (as the owner, refusing to go on unless the schema lands at `EXPECT_SCHEMA`), `swap`, `start`, `verify` and `rollback` (binaries and console from the `.rollback-<ts>` copies; the two ways to undo the database are printed, not run). The release, stage directory, target schema, rollback suffix and unit list are settings. Database URLs only reach child processes through their environment and the script refuses to run under xtrace. Usage is in `docs/runbooks/enforce-rollout.md`.
- **The PAM broker containers come back after a reboot.** `scripts/box-pam-units.sh` writes user units for `pam-guacd-ziti`, `pam-ziti-tunnel` and `pam-guacamole-ziti` (`podman start --attach` of the existing containers, the form `scripts/check-systemd-container-units.sh` prescribes, ordered on the guacd container whose network namespace the other two share) and enables them. It shows what it would do unless given `--apply`, and a second run changes nothing.
- **Remote-support sessions stay on one access-service pod.** The relay broker keeps a session's pairing, watchers and recorder in the memory of the pod that started it, and the chart runs the access service with 2-8 replicas. A separate ingress for the remote-support paths (`accessService.remoteSupport.stickyIngress`, on by default with the ingress) hashes on the session id in the path (`upstream-hash-by`), so every request and WebSocket of one session reaches the same pod; the access-service network policy admits ingress-nginx when it is on.

### Changed
- **`oidx-migrate version` only reads.** It used to create the migration ledger tables first, so as the runtime role it failed with 42501 instead of printing a number. It now reads `schema_migrations` if it exists and reports `0 (no migrations applied)` if it does not.

### Removed
- **The retired temporary access tables are dropped (migration 236).** `temp_access_links` and `temp_access_usage` go, with their policies, indexes and grants, and so does the read-only history v1.44.0 kept: `GET /api/v1/access/temp-access[/:id[/usage]]`, `DELETE /api/v1/access/temp-access/:id`, the history section under Ziti Network → Remote Access, and the kill switch's, lifecycle sweep's, deprovisioning's and JIT expiry sweep's writes to the links (the kill switch response no longer carries `pam_temp_links_revoked`). `GET /temp-access/:token` still answers every token with the static 410 page. **Export the two tables before upgrading if the history is wanted** (`pg_dump -t temp_access_links -t temp_access_usage`); the migration copies nothing. Down recreates both tables empty.

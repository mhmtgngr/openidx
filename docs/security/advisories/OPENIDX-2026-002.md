# OPENIDX-2026-002: MFA policies did not enforce their required methods, grace period or conditions

| | |
|---|---|
| **Local ID** | OPENIDX-2026-002 |
| **GHSA ID** | _to be filled in when the advisory is published_ |
| **CVE** | _none requested yet_ |
| **Status** | Draft. The fix is on `main` and in no release yet. This text is published as a GitHub security advisory when the first release after v1.36.0 is available. |
| **Issue** | [#990](https://github.com/mhmtgngr/openidx/issues/990) |

## Summary

On the MFA Management page an administrator could give an MFA policy required
methods, for example WebAuthn, and a grace period. Through the admin API a
policy could also be given conditions. Nothing enforced any of them.

From v1.34.0 the login path asks whether an enabled policy applies to the user
(`IsMFARequired`) and then discards the policy it matched. Any factor the user
has enrolled completes the challenge, so SMS or email OTP satisfied a policy
that named WebAuthn. The grace period was read by nothing. The API accepted
three conditions (`factor_enrolled`, `min_risk_score`, `client_ids`) that no
code reads, and refused the four the evaluator reads (`groups`, `ip_ranges`,
`time_windows`, `attributes`). So no condition the API accepted could narrow a
policy: it applied to every user with an enrolled factor. Before v1.34.0 the
login path did not read MFA policies at all.

## Severity

**High, 7.4.** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`

- **Attack Vector: Network.** The attacker signs in through the login
  endpoints over the network.
- **Attack Complexity: High.** The attack depends on conditions the attacker
  does not control. They need the user's password, and they must also complete
  a factor the user has enrolled that is weaker than the one the policy named:
  receive the user's SMS codes after a SIM swap, read the user's mailbox, or
  relay a one-time code phished in real time. The user must have such a factor
  enrolled. Each of these takes preparation, and none is in the attacker's
  hands alone.
- **Privileges Required: None.** The attacker starts with no session and needs
  no account of their own. The password they need is the victim's credential,
  and getting it is counted under Attack Complexity.
- **User Interaction: None.** A redirected SMS code or a read mailbox needs
  nothing from the user. Relaying a phished code would need the user to type
  it; the score takes the case that does not.
- **Scope: Unchanged.** The result is a session in OpenIDX with the user's own
  grants.
- **Confidentiality: High.** The attacker is signed in as the user. A
  requirement for WebAuthn is typically placed on administrators, whose
  sessions read the whole organization.
- **Integrity: High.** The same session makes any change the user can make.
- **Availability: None.** The flaw does not affect availability by itself.

## Weakness

**CWE-693: Protection Mechanism Failure.** The policy's method requirement is a
protection the product offered, stored and displayed, and did not apply.
CWE-308 (Use of Single-factor Authentication) was considered and not chosen:
from v1.34.0 a user who has a factor enrolled is still asked for a second
factor. The flaw is that the configured choice of factor was ignored, not that
the design uses one factor.

## Affected versions

**All versions from v1.0.0 through v1.36.0.**

- **Introduced** in commit
  [2e318cef](https://github.com/mhmtgngr/openidx/commit/2e318cef886d66ea395a54454c26bff1e3d4b4ff),
  first released in v1.0.0. It added the MFA Management page, with a
  required-methods checkbox for each method and a grace-period field, and the
  admin API that stores both. The `mfa_policies` table is older than any
  release. No version has enforced either setting.
- **v1.0.0 to v1.33.3.** `IsMFARequired` had no caller outside tests, so an
  enabled policy changed nothing at sign-in: whether a second factor was asked
  for was decided without it.
- **v1.34.0 to v1.36.0.** Commit
  [9518ee0d](https://github.com/mhmtgngr/openidx/commit/9518ee0d6b115cd1a15feb629481bd9bc6e5e6b3)
  ([#878](https://github.com/mhmtgngr/openidx/pull/878)) put `IsMFARequired`
  into the login decision and added the conditions allowlist. From then on an
  enabled policy challenges every user who has a factor enrolled, and any
  enrolled factor passes.

## Patched versions

**The first release after v1.36.0.** The fix is merge commit
[b4a3f6a4](https://github.com/mhmtgngr/openidx/commit/b4a3f6a432fb79d4ea7d639c51c4ee4f62676e46)
on `main` ([#991](https://github.com/mhmtgngr/openidx/pull/991)). No release
contains it yet.

The fix makes the product stop offering what it does not enforce:

- **API.** Creating a policy with required methods, a grace period or any
  condition answers `400`. An update may clear those fields, or send back the
  stored values, so an older policy can still be renamed and toggled.
- **Console.** The method checkboxes and the grace field are gone. The page
  says what a policy does, and flags a policy saved with such settings as
  "stored settings not enforced". The enable toggle sends only `enabled`.

**The fix does not enforce methods.** On a fixed version a policy still
challenges every user who has a second factor enrolled, and any enrolled
factor satisfies it; the product now says so. Enforcing required methods, with
a grace period, is being built as a separate change, and this advisory will be
updated when it is released. Upgrading does not change what an existing policy
does: a policy that stored methods keeps them in the database, unenforced, and
the console flags it.

## Impact

Affected: an installation with an MFA policy that was meant to require a
particular method, typically WebAuthn for administrators, or to apply only
under conditions set through the API.

An attacker who has a user's password, and can complete a weaker factor that
user has enrolled, signs in as that user where the configured WebAuthn
requirement would have stopped them. On v1.0.0 to v1.33.3 a policy did not add
a challenge at all.

In every version, fixed ones included, a policy asks nothing of a user who has
no factor enrolled. That user signs in with a password alone. The fixed MFA
Management page says so.

The unread conditions made a policy apply more widely than it said, not less.
They weakened nothing, but they were a setting that decided nothing.

## Workarounds

These are written for v1.36.0, the supported release.

1. **Read a policy as what it does.** An enabled policy asks every user who has
   a second factor enrolled for one, and accepts any factor that user has. A
   browser the user has marked as trusted skips the challenge while the login's
   risk score stays below 70. The methods and grace period that v1.36.0's MFA
   Management page shows are not enforced, and conditions set through the API
   are not read.
2. **Make the required method the only one enrolled.** For accounts that must
   use WebAuthn, have the user remove SMS and email OTP on the Security tab of
   My Profile, and TOTP or push if you do not accept those either. MFA
   Management → User MFA Status shows each user's factors. Backup codes, and
   bypass codes an administrator issues, also complete a challenge. Nothing on
   v1.36.0 stops a user from enrolling SMS or email OTP again, so check the
   list again from time to time.
3. **Find the users with no factor.** User MFA Status lists them too. A policy
   does not ask them for anything; have them enroll.
4. **Do not count on adaptive MFA to require WebAuthn.** Its method
   restriction is real: since v1.34.0 the factors a challenge may be completed
   with are fixed when the challenge is issued and checked when a factor is
   verified. But it narrows a challenge only when the risk engine itself
   requires a second factor, which with the default thresholds means a login
   scoring 30 or more. A sign-in from a known device, with no other risk
   factor, scores 0 and gets no restriction. A login scoring from 50 to 69 is
   limited to WebAuthn or push, and one scoring 70 or more to WebAuthn, but
   only for a user who has one of those enrolled: anyone else is offered, and
   may use, every factor they have. A risk policy's own `mfa_methods` list
   applies only to a login scoring from 30 to 49. Keep adaptive MFA on
   (`ADAPTIVE_MFA_ENABLED`, on by default) for the risky logins it does cover.

## How to verify the fix

- **The API refuses what it does not enforce.** As an administrator:

    ```sh
    curl -s -X POST https://openidx.example.com/api/v1/mfa/policies \
      -H "Authorization: Bearer $ADMIN_TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"name": "verify-990", "enabled": false, "required_methods": ["webauthn"]}'
    ```

    A fixed version answers `400`, saying that `required_methods` is not
    enforced. An affected version answers `201` and creates a disabled policy;
    delete it with `DELETE /api/v1/mfa/policies/<id>`. Do the same with
    `"grace_period_hours": 24`, and with `"conditions": {"client_ids": ["x"]}`,
    in place of `required_methods`.

- **The console says what a policy does.** MFA Management → MFA Policies has no
  method checkboxes or grace field, and states that any enrolled factor
  satisfies a policy. A policy saved earlier with such settings carries the
  "stored settings not enforced" badge.

- **The tests.** `TestNewMFAPolicyRefusesWhatNothingEnforces`,
  `TestMFAPolicyUpdateMayClearOrEchoButNotSet` and
  `TestMFAPolicyHandlersRefuseWhatNothingEnforces`, in
  `internal/admin/mfa_policy_conditions_test.go`, cover the API.
  `TestMFAPolicyRaisesTheLoginChallenge`, in
  `internal/oauth/mfa_policy_testdb_test.go`, covers the login path: with a
  policy on, a user whose only factor is email OTP is challenged; with it off,
  or for a user with no factor, not. The database tests need Docker, or
  `OPENIDX_TEST_DATABASE_URL` pointing at a throwaway database.

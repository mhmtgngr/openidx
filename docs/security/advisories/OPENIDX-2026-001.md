# OPENIDX-2026-001: Ending a session from the Sessions page did not revoke its refresh tokens

| **Issue** | [#992](https://github.com/mhmtgngr/openidx/issues/992) |

## Summary

Ending a session through `DELETE /api/v1/identity/sessions/:id` deleted the
session's row and nothing else. That call is behind the Sessions tab of My
Profile, and behind the My Sessions page for a user without an administrator
role.

The refresh grant does not read the session row. It decides on the refresh
token's own row and on the `revoked_session:<id>` marker in Redis, and this
path touched neither. So a device the user had signed out went on exchanging
its refresh token for new access tokens, and got a new rotated refresh token
each time. For a client with no `refresh_token_max_lifetime`, that went on for
as long as the device kept refreshing.

## Severity

**High, 7.4.** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`

- **Attack Vector: Network.** The attacker presents the refresh token at the
  token endpoint, `POST /oauth/token`, from anywhere that endpoint is reachable.
- **Attack Complexity: High.** The attack depends on conditions the attacker
  does not control. They must already hold a refresh token issued to the
  victim's session: they have the signed-in device, or a copy of the token
  taken from it. And the victim must end that session through the affected
  path rather than another one. For a confidential client, the attacker also
  needs the client secret; the desktop and mobile apps are public clients, for
  which the token alone is enough.
- **Privileges Required: None.** The attacker needs no account or role of their
  own. What they hold is the victim's credential, and once the victim has ended
  the session they are not meant to be authorized at all. Getting hold of that
  credential is counted under Attack Complexity, not here.
- **User Interaction: None.** Nothing is asked of the victim for the refresh to
  succeed.
- **Scope: Unchanged.** The flaw is in the OpenIDX token service, and what it
  yields is the access OpenIDX grants the user. It does not reach past that
  authority.
- **Confidentiality: High.** Each refresh returns an access token with the
  user's roles and the scopes granted to the client, for as long as the chain
  lasts. The reasonable worst case is an administrator's session, which reads
  the whole organization through the admin API.
- **Integrity: High.** The same tokens make any change the user can make; for an
  administrator, that is any change in the organization.
- **Availability: None.** The flaw does not affect availability by itself.

## Weakness

**CWE-613: Insufficient Session Expiration.** The credential of a session
stayed usable after the session was ended: the refresh token of a session the
user had signed out went on minting access tokens. That is the reuse of an old
session credential that CWE-613 describes.

## Affected versions

**v1.1.0 through v1.36.0.**

- **Introduced** in commit
  [bcf263f3](https://github.com/mhmtgngr/openidx/commit/bcf263f3e0c80155bc697f551e510cdb6041bb62)
  ([#114](https://github.com/mhmtgngr/openidx/pull/114)), first released in
  v1.1.0. It added migration 31, which gives `oauth_refresh_tokens` a
  `session_id` column with no foreign key, and refresh-token rotation. The two
  halves it joined were older and both in v1.0.0: `TerminateSession` has
  deleted only the session row since the first commit
  ([4c7a8214](https://github.com/mhmtgngr/openidx/commit/4c7a8214373bc1016334486981f1dacf8cab6544)),
  and the refresh grant has asked only the Redis marker about a token's
  session since refresh tokens were bound to sessions
  ([09b5db8c](https://github.com/mhmtgngr/openidx/commit/09b5db8ce048c5e8a43ea7c03602da145e64de3e)).

- **v1.0.0 is not affected.** On a schema built by the migration runner the
  table had no `session_id` column, so every refresh-token insert failed and
  every refresh answered `invalid_grant` (#114 describes this). On the Docker
  Compose schema, built from
  [`init-db.sql`](https://github.com/mhmtgngr/openidx/blob/v1.10.1/deployments/docker/init-db.sql),
  the column referenced `sessions(id)` with `ON DELETE CASCADE`, so deleting
  the session row deleted its refresh tokens.

- **A database first created from `init-db.sql` may not be affected.** Docker
  Compose built its schema from that file until v1.11.0
  ([84f16627](https://github.com/mhmtgngr/openidx/commit/84f166274732bcc96eba99b7fa6646657dd8eeee),
  [#303](https://github.com/mhmtgngr/openidx/pull/303)), and no migration drops
  the foreign key. Where it is present, ending a session deleted its refresh
  tokens. A database built by the migration runner (the Helm chart's migrate
  job, and Docker Compose from v1.11.0) has no such key. To check yours:

    ```sql
    SELECT conname, pg_get_constraintdef(oid)
      FROM pg_constraint
     WHERE conrelid = 'oauth_refresh_tokens'::regclass AND contype = 'f';
    ```

    A row reading `FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE
    CASCADE` means this path was not open on that database.

- **Who could reach the path.** From v1.0.0 the identity admin API, this route
  included, required the `admin` or `super_admin` role
  ([1c28175c](https://github.com/mhmtgngr/openidx/commit/1c28175c07659c1b0da616c76c2d9434b4bf1f23)).
  From v1.1.0 to v1.27.x the affected callers were therefore administrators,
  ending a session from their own profile or through the API. v1.28.0
  ([fdfe2e2f](https://github.com/mhmtgngr/openidx/commit/fdfe2e2f20639c17e01f5f6310e8f3b9ff2a56d4),
  [#660](https://github.com/mhmtgngr/openidx/pull/660)) let any user end their
  own sessions this way.

- **How long a chain lasts.** Rotation restarts a refresh token's lifetime on
  every use, so a device that keeps refreshing is never stopped by it. v1.35.0
  ([ea4bc464](https://github.com/mhmtgngr/openidx/commit/ea4bc46416e1b543b2715f6a5fb6276b721c9dfa),
  migration v187) capped the whole chain at 90 days for the three native
  clients as seeded (`openidx-mobile`, `openidx-agent-android`,
  `openidx-desktop`). Any other client has no cap unless its
  `refresh_token_max_lifetime` is set.

## Patched versions

**v1.37.0**, released on 2026-09-25
([release](https://github.com/mhmtgngr/openidx/releases/tag/v1.37.0)). The
fix is merge commit
[f181b726](https://github.com/mhmtgngr/openidx/commit/f181b726b74183c5704c929e4a012ec90637f7d7)
on `main` ([#993](https://github.com/mhmtgngr/openidx/pull/993)).

`identity.TerminateSession` now revokes the session's refresh tokens in the
database, which holds with Redis down, then publishes the
`revoked_session:<id>` marker, and only then deletes the row. If the refresh
tokens cannot be revoked, the session is not deleted and the request fails.

**Upgrading reaches back too.** The same release carries the fix for
[OPENIDX-2026-004](OPENIDX-2026-004.md), which makes the refresh grant refuse a
token whose session row is gone. So refresh tokens of sessions ended through
this path before the upgrade stop working once oauth-service runs the new
version. The query in Workarounds still revokes their rows, which is worth
doing once after upgrading: a revoked row is refused without reading the
sessions table.

## Impact

A user who ended a session expected the device to be signed out. It was not,
if the session's client held a refresh token: a client that is allowed refresh
tokens and was granted `offline_access`. The OpenIDX desktop and mobile apps
ask for it, and so can any application an operator registers with it. The
admin console does not ask for it and holds no refresh token. Whoever held the
device, or a copy of its refresh token, kept getting access tokens with the
user's roles and scopes. This is the case the Sessions page exists for: a lost
or stolen laptop or phone.

The affected actions, on v1.28.0 and later:

- ending one session from the Sessions tab of My Profile;
- **Revoke All Sessions** on that tab, which ends each session the same way;
- ending a session from the My Sessions page, for a user without an
  administrator role;
- any client calling `DELETE /api/v1/identity/sessions/:id`.

An access token already minted stays valid until it expires, one hour by
default. That was true before the fix and still is; this advisory is about the
refresh tokens, which had no end.

The other ways a session ends do not go through `TerminateSession` and are
not part of this advisory: **Revoke** and **Revoke All** on the admin
console's Sessions page, Sign Out Everywhere, disabling or deleting the user,
deprovisioning and the kill switch. Before v1.34.0 the admin console's revoke
had a gap of its own: it marked the session revoked without publishing the
marker. That was fixed in v1.34.0
([6002910f](https://github.com/mhmtgngr/openidx/commit/6002910f1cd8cc8bfd1f81254f5b16845b5b66ce)).

## Workarounds

These are written for v1.36.0, the last affected release. The supported
release is v1.37.0, which needs none of them.

1. **Revoke the refresh tokens of sessions that no longer exist.** This also
   covers sessions already ended through the affected path, which the upgrade
   does not reach. Run it now, again after any use of the affected path, and
   once after upgrading. Use `psql` as the role that owns the schema;
   `app.bypass_rls` lets the statement see every tenant's rows.

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    -- Look first: live refresh tokens whose session row is gone.
    SELECT org_id, user_id, client_id, session_id, created_at, expires_at
      FROM oauth_refresh_tokens t
     WHERE t.session_id IS NOT NULL
       AND t.revoked_at IS NULL
       AND NOT EXISTS (SELECT 1 FROM sessions s WHERE s.id = t.session_id);
    -- Then revoke them.
    UPDATE oauth_refresh_tokens t
       SET revoked_at = NOW()
     WHERE t.session_id IS NOT NULL
       AND t.revoked_at IS NULL
       AND NOT EXISTS (SELECT 1 FROM sessions s WHERE s.id = t.session_id);
    COMMIT;
    ```

    The statement touches only tokens whose session is gone. Nothing deletes
    a session row except a path that ends the session, and session expiry
    marks a row revoked rather than deleting it. So a refresh token whose
    session row is gone belongs to a session somebody ended.

2. **A user signing a device out: use Sign Out Everywhere.** It is on the
   Sessions tab of My Profile and calls `POST /oauth/logout-all`. It revokes
   all of the user's sessions and deletes all of their refresh tokens in the
   database, so it holds with Redis down, and it also reaches a session the
   user already ended through the affected path. It signs the user out on
   every device, including the one in use. Do not use **Revoke All Sessions**
   on the same tab: it ends each session through the affected path.

3. **An administrator: use the admin console's Sessions page.** **Revoke**
   (`DELETE /api/v1/sessions/:id`) and **Revoke All**
   (`DELETE /api/v1/users/:id/sessions`) mark the sessions revoked and publish
   their `revoked_session:<id>` markers, which the refresh grant checks. They
   do not revoke the refresh tokens in the database, so the refresh is refused
   only while Redis holds the marker, which is written to last 30 days. The
   response carries a warning when a marker could not be written. They act
   only on sessions whose rows still exist; a session already ended through
   the affected path no longer appears there, and step 1 is what reaches it.

4. **Last resort: disable the account.** The refresh grant checks that the
   user is enabled on every refresh, so disabling the user stops every chain
   at once.

## How to verify the fix

- **The test.** `TestAnEndedSessionCannotRefresh`, in
  `internal/oauth/session_end_refresh_testdb_test.go`, creates a session the
  way login does, ends it with `identity.TerminateSession` and presents its
  refresh token. The refresh is refused with Redis up and with Redis down, and
  the user's other session keeps refreshing. Run
  `go test ./internal/oauth -run TestAnEndedSessionCannotRefresh` with Docker
  available, or with `OPENIDX_TEST_DATABASE_URL` pointing at a throwaway
  database: the test drops and recreates its `public` schema.

- **On a running install.** Sign in as an ordinary test user from a client
  that holds a refresh token: the desktop or mobile app, or a test application
  whose login asks for `offline_access`. List the user's live refresh tokens:

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    SELECT session_id, client_id, created_at FROM oauth_refresh_tokens
     WHERE user_id = '<user id>' AND revoked_at IS NULL;
    COMMIT;
    ```

    Then sign in to the console as the same user and end that session under
    My Profile → Sessions. Run the query again. On a fixed version the ended
    session's tokens are no longer listed. On an affected version they still
    are, and the client goes on refreshing.

    If you hold the client's current refresh token, present it directly:

    ```sh
    curl -s -X POST https://auth.example.com/oauth/token \
      -d grant_type=refresh_token \
      -d client_id="$CLIENT_ID" \
      -d refresh_token="$REFRESH_TOKEN"
    ```

    A fixed version answers `400` with `"error":"invalid_grant"`. An affected
    version answers `200` with a new access token and refresh token.

# OPENIDX-2026-005: `POST /oauth/force-login` ended any session whose id it was sent

## Summary

`POST /oauth/force-login` serves the concurrent-session limit's **Ask User to
Choose** strategy: a user whose sign-in reaches the limit names one of their
sessions, and the endpoint ends it and completes the sign-in. The endpoint
takes no credentials; the pending sign-in it is given (`login_session`) is what
says who is asking. But it ended the session named by `terminate_session_id`
before it read the pending sign-in. So anyone who knew a session's id could end
that session, whoever it belonged to, with no sign-in of their own.

A session id is a random UUID, and cannot be guessed. It is not a secret
either: it is the `sid` claim of every access token and ID token issued for the
session, so every application and API those tokens were sent to holds it, and
it outlives the tokens that carried it. Administrators see session ids in the
admin API's list of sessions, and the services write them to their logs.

## Severity

**Low, 3.7.** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L`

- **Attack Vector: Network.** The endpoint is on the OAuth service, reachable
  wherever sign-in is.
- **Attack Complexity: High.** The attacker must know the id of the session
  they want to end, and cannot guess it. They must be where it can be seen: an
  application or API the user's tokens were sent to, the holder of one of those
  tokens, even an expired one, an administrator, or a reader of the services'
  logs.
- **Privileges Required: None.** The request takes no credentials, and on an
  affected version not even a pending sign-in: the session is ended before
  anything else in the request is read.
- **User Interaction: None.** Nothing is asked of the user.
- **Scope: Unchanged.** The effect is on the user's OpenIDX session.
- **Confidentiality: None.** Nothing is disclosed.
- **Integrity: None.** Nothing the user or the organization holds is changed.
  The session's end is the whole effect, and it is counted under Availability.
- **Availability: Low.** The user is signed out of that one session: its
  refresh tokens are refused for the next 25 hours, so a device using it has to
  sign in again, which it can. To sign them out again, the attacker needs the
  new session's id.

## Weakness

**CWE-639: Authorization Bypass Through User-Controlled Key.** The request
named the session to end, and the endpoint acted on that name without checking
that the session belonged to the sign-in making the request.

## Affected versions

**v1.0.0 through v1.36.0.**

- **Introduced** in commit
  [09b5db8c](https://github.com/mhmtgngr/openidx/commit/09b5db8ce048c5e8a43ea7c03602da145e64de3e),
  first released in v1.0.0, which added the concurrent-session limit and this
  endpoint. The endpoint is registered in every configuration, whether or not a
  limit is set, so every installation is affected.

## Patched versions

**v1.37.0.** The fix is merge commit
[690b622e](https://github.com/mhmtgngr/openidx/commit/690b622ec493c528934542b9a8478ab77b63ecc0)
([#1008](https://github.com/mhmtgngr/openidx/pull/1008)),
and v1.37.0 is the first release that contains it.

The endpoint now reads the pending sign-in first. It refuses one that is
missing (`400 login_session_expired`) or that no password check has completed
(`400 invalid_request`). It ends the named session only if it is a live session
of that same user, in the same organization; otherwise it answers
`400 invalid_request` and ends nothing, with the same answer whether the id is
unknown, another user's or already ended.

## Impact

Anyone who holds a user's session id can sign that session out. The session is
marked revoked and leaves the user's list of sessions, and the refresh grant
refuses its refresh tokens for 25 hours, so a desktop or mobile app signed in
under it has to sign in again. Nothing is disclosed and no access is gained. An
access token already issued stays valid until it expires.

## Workarounds

These are written for v1.36.0, the last release without the fix.

1. **Block `POST /oauth/force-login` at the reverse proxy or ingress in front
   of the OAuth service, unless you use Ask User to Choose.** Nothing else calls
   it: the sign-in page calls it only from that strategy's prompt, and the
   desktop and mobile apps do not call it. With **Max Concurrent Sessions** at
   0, which is unlimited and the default, or with the **Deny New Login** or
   **Terminate Oldest Session** strategy, blocking it changes nothing for
   users.

2. **If you use Ask User to Choose, switch to Deny New Login** on the Security
   tab of Settings, and block the endpoint as in 1. A sign-in over the limit is
   then refused, instead of asked which session to end.

## How to verify the fix

- **The test.** `TestForceLoginEndsOnlyASessionOfTheUserSigningIn`, in
  `internal/oauth` (`force_login_testdb_test.go`, added by #1008), sends the
  endpoint another user's session, an id that names no session, a pending
  sign-in that does not exist and one that no password check completed. Each is
  refused, and the other user's session stays live, with no refresh token
  revoked and no marker written. The user's own live session is ended and the
  sign-in resumes; an own session that has already ended is refused. Run
  `go test ./internal/oauth -run TestForceLoginEndsOnlyASessionOfTheUserSigningIn`
  with Docker available, or with `OPENIDX_TEST_DATABASE_URL` pointing at a
  throwaway database: the test drops and recreates its `public` schema.

- **On a running install.** Sign in to the console as a test user, and read the
  `sid` claim from their access token (the middle part of the JWT, base64url
  decoded). Then, from anywhere and with no credentials:

    ```sh
    curl -s -X POST https://auth.example.com/oauth/force-login \
      -H 'Content-Type: application/json' \
      -d '{"terminate_session_id": "<sid>", "login_session": "none"}'
    ```

    Both versions answer `400` with `"error":"login_session_expired"`. Look at
    the test user's sessions under My Profile → Sessions straight away: on a
    fixed version the session is still listed, and on an affected version it is
    gone.

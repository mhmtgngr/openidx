# OPENIDX-2026-004: Refresh tokens survived password changes and the other ways a session ends

## Summary

The refresh grant decides on the refresh token's own row and on the
`revoked_session:<id>` marker in Redis. It does not read the session's row.
[OPENIDX-2026-001](OPENIDX-2026-001.md) was one way of ending a session that
left its refresh tokens working: ending it from the Sessions tab of My Profile.
Most of the other ways did the same, and a password change, which should have
ended sessions, ended none:

- **A password change or reset** ended no session, although the Security tab
  of Settings showed a **Force logout on password change** switch, on by
  default. Nothing read it.
- **The lifecycle action `revoke_sessions` and breach containment** ended
  sessions and wrote no marker, so the refresh tokens of an account they left
  enabled kept working at once.
- **The expiry and inactivity sweeps, concurrent-session eviction and
  force-login** wrote a marker that lives 25 hours, and **a replayed refresh
  token** marked its session for 24 hours. Tokens that outlive the marker, such
  as the desktop and mobile apps', worked again once it expired.
- **Revoke and Revoke All on the admin console's Sessions page, the kill switch
  and the device revoke** wrote a marker that lives 30 days. The tokens worked
  again whenever Redis was unreachable at the refresh or had lost the marker.

Each refresh that got through returned a new access token and a new rotated
refresh token, so a device that got through once went on refreshing.

## Severity

**High, 7.4.** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`

- **Attack Vector: Network.** The attacker presents the refresh token at the
  token endpoint, `POST /oauth/token`, from anywhere that endpoint is reachable.
- **Attack Complexity: High.** The attack depends on conditions the attacker
  does not control. They must already hold a refresh token issued to the
  victim's session: they have the signed-in device, or a copy of the token
  taken from it. Then the session must end through one of the affected paths,
  or the password be changed. These arise in the ordinary course: the timeouts
  end sessions on their own, and a password change or an administrator's revoke
  is what follows a suspected compromise. For the paths that write a marker,
  the attacker must also wait for it to expire or reach the token endpoint
  while Redis is without it. For a confidential client, the
  attacker also needs the client secret; the desktop and mobile apps are public
  clients, for which the token alone is enough.
- **Privileges Required: None.** The attacker needs no account or role of their
  own. What they hold is the victim's credential, and once the session has
  ended they are not meant to be authorized at all. Getting hold of that
  credential is counted under Attack Complexity, not here.
- **User Interaction: None.** Nothing is asked of the victim for the refresh to
  succeed.
- **Scope: Unchanged.** The flaw is in the OpenIDX token service, and what it
  yields is the access OpenIDX grants the user. It does not reach past that
  authority.
- **Confidentiality: High.** Each refresh returns an access token with the
  user's roles and the scopes granted to the client, for as long as the chain
  lasts. The reasonable worst case is an administrator's session, which reads
  the whole organization through the admin API.
- **Integrity: High.** The same tokens make any change the user can make; for an
  administrator, that is any change in the organization.
- **Availability: None.** The flaw does not affect availability by itself.

## Weakness

**CWE-613: Insufficient Session Expiration.** The credential of a session
stayed usable after the session ended, and after the password it was issued
under was changed: the refresh tokens of sessions that had timed out, been
revoked or been contained went on minting access tokens, and so did those of a
user whose password had been changed or reset.

## Affected versions

**v1.0.0 through v1.36.0.**

- **Introduced** in commit
  [09b5db8c](https://github.com/mhmtgngr/openidx/commit/09b5db8ce048c5e8a43ea7c03602da145e64de3e),
  first released in v1.0.0. It bound refresh tokens to sessions and gave the
  refresh grant its one check of a token's session, the Redis marker. It also
  added the expiry and inactivity sweeps and the concurrent-session limit, with
  its eviction and force-login, each of which marks the session's row revoked
  and writes a 25-hour marker, and a function to end a user's sessions on a
  password change, which no release called before v1.37.0. The lifecycle
  action and breach containment were in v1.0.0 too. The kill switch (v1.25.0),
  refresh-token replay detection (v1.28.0) and the device revoke (v1.35.0) came
  later, each with the gap described under Impact.

- **On v1.0.0 only a database built from `init-db.sql` was affected.** One built
  by the migration runner could not store a refresh token until v1.1.0
  ([bcf263f3](https://github.com/mhmtgngr/openidx/commit/bcf263f3e0c80155bc697f551e510cdb6041bb62),
  [#114](https://github.com/mhmtgngr/openidx/pull/114));
  [OPENIDX-2026-001](OPENIDX-2026-001.md) explains. On a database that still
  has `init-db.sql`'s foreign key from `oauth_refresh_tokens.session_id` to
  `sessions`, deleting a session deletes its refresh tokens, so the lifecycle
  action, which deletes the rows, did not leave them there. The other paths
  mark the row revoked and did.

- **Revoke and Revoke All on the console's Sessions page wrote no marker at all
  before v1.34.0**
  ([6002910f](https://github.com/mhmtgngr/openidx/commit/6002910f1cd8cc8bfd1f81254f5b16845b5b66ce)),
  so until then their refresh tokens kept working at once.

- **How long a chain lasts.** As for OPENIDX-2026-001: rotation restarts a
  refresh token's lifetime on every use. From v1.35.0 the three native clients
  as seeded cap a chain at 90 days; any other client has no cap unless its
  `refresh_token_max_lifetime` is set.

## Patched versions

**v1.37.0.** The fix is merge commit
[690b622e](https://github.com/mhmtgngr/openidx/commit/690b622ec493c528934542b9a8478ab77b63ecc0)
([#1008](https://github.com/mhmtgngr/openidx/pull/1008)),
and v1.37.0 is the first release that contains it.

- **Every path above revokes the session's refresh tokens in the database**,
  which holds with Redis down, before or in the same transaction as the
  statement that ends the session, and still writes the marker. A replay
  revokes every chain of its session.
- **A password change ends the user's other sessions** and keeps the one it
  was made from. A reset (the forgotten-password link, an administrator setting
  a password, an administrator resetting a directory account) ends all of
  them. Both revoke every refresh token of the user but the kept session's,
  including tokens bound to no session, and cut the user's outstanding access
  tokens at userinfo and introspection. The **Force logout on password change**
  switch is removed: a change or reset always ends sessions.
- **The refresh grant reads the session.** A refresh token bound to a session is
  refused (`invalid_grant`, `session_revoked`), and revoked, unless the
  session's row exists in the token's organization, is not revoked and has not
  expired. If the row cannot be read, nothing is minted. Tokens bound to no
  session, which the device authorization grant issues, are unaffected.
- **A refresh records activity on the session again**, and the sweep enforces
  the Security tab's absolute timeout, counted from sign-in, which v1.36.0
  showed and did not read.
- A census test fails on a new function that ends sessions without revoking
  their refresh tokens, unless it is registered with a reason.

**Upgrading reaches back, except for password changes.** The grant's check of
the session refuses the tokens of sessions ended before the upgrade from the
first request; no query is needed. A password change or reset made before the
upgrade ended no session, and upgrading does not end them: Workarounds 2 does.

**Timeouts now sign the desktop and mobile apps out for good.** A session ended
by the idle or absolute timeout takes its refresh tokens with it. The idle
timeout counts from the last refresh, so it should be longer than the
access-token lifetime of a client that refreshes only when its token runs out;
the default idle timeout, 30 minutes, is shorter than the default access-token
lifetime, one hour. To keep those apps signed in across a longer quiet period,
raise the idle and absolute timeouts on the Security tab of Settings.

## Impact

A user or administrator who ended a session, or changed a password, expected
the devices signed in under it to be signed out. They were not, if the
session's client held a refresh token: a client that is allowed refresh tokens
and was granted `offline_access`, such as the OpenIDX desktop and mobile apps.
Whoever held the device, or a copy of its refresh token, kept getting access
tokens with the user's roles and scopes.

The paths, on v1.36.0:

- **Password change and reset: every refresh token kept working.** A user
  changing their own password on the Security tab of My Profile, for a local or
  a directory account; the forgotten-password link; an administrator setting a
  password (`POST /api/v1/identity/users/:id/set-password`); an administrator
  resetting a directory account's password. None ended a session, including the
  one on the device of whoever the change was meant to keep out.
- **At once:** the lifecycle action `revoke_sessions`, which deleted the user's
  session rows, and breach containment, which marked the affected users'
  sessions revoked. Neither wrote a marker. The full quarantine of a critical
  incident also disables the accounts, which the refresh grant refuses; the
  containment of a high or medium one does not.
- **After 25 hours:** the expiry sweep, the inactivity sweep, and the
  concurrent-session limit's **Terminate Oldest Session**, and **Ask User to
  Choose**, where the user names a session to end (`POST /oauth/force-login`).
  Each marked the row revoked and wrote a marker that lives 25 hours. A token
  whose own lifetime is longer worked again once the marker expired: the
  desktop and mobile apps' tokens live 14 to 30 days, and an administrator can
  give any client a longer lifetime than the default 24 hours. On `main` after
  v1.36.0, signing out with the single sign-on cookie ended a session the same
  way; that path is in no release.
- **After 24 hours:** a replayed refresh token. The replay revoked the replayed
  chain and marked its session for 24 hours; any other chain of the session
  worked again once the marker expired.
- **Whenever Redis was without the marker:** **Revoke** and **Revoke All** on
  the console's Sessions page, the kill switch, and the device revoke for the
  other chains of the sessions it ended (it revoked the device's own chains in
  the database). They wrote a marker that lives 30 days, which outlives the
  refresh tokens of every client as seeded. So these tokens worked again only
  while Redis was unreachable at the refresh, or after it had lost the marker
  (it restarted without persistence, was flushed or evicted the key), or for a
  client given refresh tokens that live longer than 30 days.

Every path that relied on a marker, whatever its lifetime, was open in the same
way while Redis was without it: the refresh grant reads a Redis error as "no
marker".

**On v1.36.0 the inactivity sweep reached most sessions of the desktop and
mobile apps.** A refresh did not record activity on the session, which #1008
also fixes, so the sweep ended a session once the idle timeout, 30 minutes by
default, had passed since sign-in, while it was still in use. The app's next
refresh was refused while the marker lived; once it expired, 25 hours after the
sweep, the same refresh token, or a copy of it, refreshed again.

An access token already minted stays valid until it expires, one hour by
default. That was true before the fix and still is; this advisory is about the
refresh tokens.

Not part of this advisory: ending a session from the Sessions tab of My Profile
or the My Sessions page, which is OPENIDX-2026-001; Sign Out Everywhere,
sign-out through `/oauth/logout` with an ID token or an access token, and a
session revoked by a Shared Signals event, which also delete the user's refresh
tokens; and disabling, deleting or deprovisioning the user.

## Workarounds

These are written for v1.36.0, the last release without the fix.

1. **Revoke the refresh tokens of every session that has ended.** A session has
   ended when its row is gone, revoked or expired, which is the test the fixed
   refresh grant applies. This covers every path above except a password
   change, which ended no session, and a replay, which left the row live, and
   it takes in the sessions OPENIDX-2026-001 is about. Run it now, again right
   after a lifecycle `revoke_sessions` or a breach containment, which write no
   marker, and on a schedule, hourly for example, for the rest. Use `psql` as
   the role that owns the schema; `app.bypass_rls` lets the statement see every
   tenant's rows.

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    -- Look first: live refresh tokens whose session has ended.
    SELECT t.org_id, t.user_id, t.client_id, t.session_id, t.created_at, t.expires_at
      FROM oauth_refresh_tokens t
     WHERE t.session_id IS NOT NULL
       AND t.revoked_at IS NULL
       AND NOT EXISTS (SELECT 1 FROM sessions s
                        WHERE s.id = t.session_id AND s.org_id = t.org_id
                          AND COALESCE(s.revoked, false) = false
                          AND s.expires_at > NOW());
    -- Then revoke them.
    UPDATE oauth_refresh_tokens t
       SET revoked_at = NOW()
     WHERE t.session_id IS NOT NULL
       AND t.revoked_at IS NULL
       AND NOT EXISTS (SELECT 1 FROM sessions s
                        WHERE s.id = t.session_id AND s.org_id = t.org_id
                          AND COALESCE(s.revoked, false) = false
                          AND s.expires_at > NOW());
    COMMIT;
    ```

    It leaves alone the tokens of live sessions, and the tokens bound to no
    session, which the device authorization grant issues. An app whose session
    the inactivity sweep ended is refused already while the marker lives; after
    this it stays refused, and its user signs in again.

2. **After a password change or reset, end the user's sessions yourself.** The
   user can use **Sign Out Everywhere** on the Sessions tab of My Profile
   (`POST /oauth/logout-all`). It revokes all of their sessions and deletes all
   of their refresh tokens in the database, and it signs them out on every
   device, including the one in use. An administrator can revoke every refresh
   token the user holds, bound to a session or not:

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    UPDATE oauth_refresh_tokens SET revoked_at = NOW()
     WHERE user_id = '<user id>' AND revoked_at IS NULL;
    COMMIT;
    ```

    Then use **Revoke All** for the user on the console's Sessions page, so
    that their sessions show as ended.

3. **After a refresh-token replay, revoke the rest of its session.** The
   `oauth.refresh_token.reuse_detected` webhook event, and oauth-service's log
   line `SECURITY: refresh token reuse detected`, carry the `session_id`:

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    UPDATE oauth_refresh_tokens SET revoked_at = NOW()
     WHERE session_id = '<session id>' AND revoked_at IS NULL;
    COMMIT;
    ```

## How to verify the fix

- **The tests.** #1008 adds one test in `internal/oauth` for each group of
  paths. Each ends a session the way those paths do and presents its refresh
  token at the token endpoint, with Redis down or the marker expired where the
  path used to depend on it, and checks that an unrelated session keeps
  refreshing. Run them with Docker available, or with
  `OPENIDX_TEST_DATABASE_URL` pointing at a throwaway database: the tests drop
  and recreate its `public` schema.

    ```sh
    go test ./internal/oauth -run 'TestAPasswordChangeEndsEveryOtherSession|TestAPasswordResetEndsEverySession|TestLifecycleRevokeSessionsEndsTheRefreshPath|TestASessionOAuthEndedStaysEndedAfterItsMarkerExpires|TestARefreshReplayEndsEveryChainOfItsSession|TestAnAdministratorEndingSessionsStopsTheirRefresh|TestTheRefreshGrantRequiresALiveSession'
    ```

    - `TestAPasswordChangeEndsEveryOtherSession`: the session the change was
      made from keeps refreshing, and the user's others do not.
    - `TestAPasswordResetEndsEverySession`: the forgotten-password link, an
      administrator setting a password, and an administrator resetting a
      directory account.
    - `TestLifecycleRevokeSessionsEndsTheRefreshPath`.
    - `TestASessionOAuthEndedStaysEndedAfterItsMarkerExpires`: the expiry,
      inactivity and absolute-timeout sweeps, eviction, force-login and
      sign-out with the single sign-on cookie, after the 25-hour marker.
    - `TestARefreshReplayEndsEveryChainOfItsSession`.
    - `TestAnAdministratorEndingSessionsStopsTheirRefresh`: Revoke, Revoke All,
      breach containment, the kill switch and the device revoke.
    - `TestTheRefreshGrantRequiresALiveSession`: the grant's reading of the
      session.

    `TestEveryPathThatEndsSessionsRevokesTheirRefreshTokens`, in
    `internal/common/sessionend`, is the census. It reads the source and needs
    no database.

- **On a running install.** Sign in as an ordinary test user from a client
  that holds a refresh token: the desktop or mobile app, or a test application
  whose login asks for `offline_access`. List the user's live refresh tokens:

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    SELECT session_id, client_id, created_at FROM oauth_refresh_tokens
     WHERE user_id = '<user id>' AND revoked_at IS NULL;
    COMMIT;
    ```

    Then sign in to the console as the same user and change their password on
    the Security tab of My Profile. Run the query again. On a fixed version the
    app's tokens are no longer listed. On an affected version they still are,
    and the app goes on refreshing.

    If you hold the app's current refresh token, present it directly:

    ```sh
    curl -s -X POST https://auth.example.com/oauth/token \
      -d grant_type=refresh_token \
      -d client_id="$CLIENT_ID" \
      -d refresh_token="$REFRESH_TOKEN"
    ```

    A fixed version answers `400` with `"error":"invalid_grant"`. An affected
    version answers `200` with a new access token and refresh token.

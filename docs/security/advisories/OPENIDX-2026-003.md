# OPENIDX-2026-003: A sign-in link let users who needed a second factor sign in without one

## Summary

The sign-in page offers **Email me a sign-in link**. It asks
`POST /oauth/magic-link` to email the user a one-time link (a magic link), and
following the link, `GET /oauth/magic-link-verify`, completes the pending
sign-in: the handler checks the link, creates a session and redirects to the
application with an authorization code.

It did that without asking whether the user needed a second factor. The
password sign-in asks for one from a user with TOTP enrolled, and from a user
with any factor enrolled whom an enabled MFA policy covers or whose login the
risk engine flags. It refuses outright a login the risk engine denies. The link
skipped all of that, so whoever could read a user's email could sign in as that
user with neither the password nor the second factor. That is the case a second
factor exists for: without the link, a mailbox gets an attacker a password
reset, and the second factor still stands in the way.

## Severity

**High, 7.4.** `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`

- **Attack Vector: Network.** The attacker asks for the link and follows it at
  the OAuth service's public endpoints, from anywhere they are reachable.
- **Attack Complexity: High.** The attack depends on conditions the attacker
  does not control. They must read mail sent to the user's address: have
  access to the user's mailbox, through a compromised or shared mail account or
  a forwarding rule, or to the message on its way. The user must be one the
  password sign-in asks for a second factor. And the installation must send
  email and leave sign-in links on, which it does by default. Getting into a
  mailbox takes preparation and is not in the attacker's hands alone.
- **Privileges Required: None.** The attacker needs no account of their own.
  The mailbox is the user's credential, and getting into it is counted under
  Attack Complexity.
- **User Interaction: None.** The attacker asks for the link and follows it.
  Nothing is asked of the user, who at most sees an email they did not ask for.
- **Scope: Unchanged.** The result is a sign-in as the user, to the
  application whose sign-in the attacker started, with the user's own grants.
- **Confidentiality: High.** The attacker is signed in as the user. A second
  factor is typically required of administrators, whose sessions read the whole
  organization.
- **Integrity: High.** The same session makes any change the user can make.
- **Availability: None.** The flaw does not affect availability by itself.

## Weakness

**CWE-288: Authentication Bypass Using an Alternate Path or Channel.** The
password sign-in required a second factor of these users, and the sign-in link
was a second way into the same sign-in that did not. CWE-308 (Use of
Single-factor Authentication) describes what the link amounted to for them, and
was considered and not chosen: the product does ask for the second factor on
its main path, and the flaw is the path around it.

## Affected versions

**v1.28.0 through v1.36.0.**

- **Introduced** in commit
  [61ab6579](https://github.com/mhmtgngr/openidx/commit/61ab6579db198977bcca71d620b87ea3d7b46035)
  ([#513](https://github.com/mhmtgngr/openidx/pull/513)), first released in
  v1.28.0. It made `POST /oauth/magic-link` send the link by email. The handler
  that completes the sign-in when the link is followed is older: it was added in
  [da1abbc2](https://github.com/mhmtgngr/openidx/commit/da1abbc28fb39b3cf75c2ad97ccba75456a364f0),
  in v1.0.0, and in no version before the fix did it ask for a second factor.

- **v1.0.0 to v1.27.x are not affected.** Their `POST /oauth/magic-link`
  created the link and did not send it; only a development build with debug
  one-time codes turned on wrote it to the log. Before v1.3.0 the handler also
  turned away every real `login_session`
  ([#125](https://github.com/mhmtgngr/openidx/issues/125)).

- **Reachable by default.** Both routes are public and registered in every
  configuration, and the sign-in page offers the link to anyone. Sign-in links
  are on unless an administrator turns them off. Before v1.35.0 the **Magic
  Links** switch on the Passwordless page was not read
  ([d202f036](https://github.com/mhmtgngr/openidx/commit/d202f03623cf8a83ee5eef2b8b353d555b754979)),
  so it could not turn them off. Only an installation that sends email delivers
  the link.

- **Whom the link let in without a second factor.** On v1.28.0 to v1.33.x the
  password sign-in asks for a second factor from a user with TOTP enrolled, and
  from a user with any factor enrolled whose login the risk engine flags; a
  browser the user chose to trust can stand in for it. From v1.34.0
  ([9518ee0d](https://github.com/mhmtgngr/openidx/commit/9518ee0d6b115cd1a15feb629481bd9bc6e5e6b3),
  [#878](https://github.com/mhmtgngr/openidx/pull/878)) it also asks every user
  with a factor enrolled whom an enabled MFA policy covers
  ([OPENIDX-2026-002](OPENIDX-2026-002.md) has the detail). The link let each
  of them in with the link alone. A user the password sign-in does not ask for a
  second factor, such as one with no factor enrolled, is not affected: for them
  the link is the passwordless sign-in it is meant to be.

## Patched versions

**The first release that contains PR #1007.** The fix is PR
[#1007](https://github.com/mhmtgngr/openidx/pull/1007), merge commit
_merge commit to be filled in_. No release contains it yet.

After the link is checked, and before a session is created, the handler now
asks the password sign-in's own decision (`evaluateMFA`) about the user, so the
two cannot disagree. A user that decision would ask for a second factor, refuse
under an MFA policy whose grace period is over, or refuse on risk goes back to
the sign-in page for the same pending request, with the reason in `?error=`
(`mfa_required`, `mfa_enrollment_required` or `high_risk_login`), to sign in
with their password and second factor. The sign-in page now says why. The link
is spent either way, and the refusal is audited as `magic_link_login` with the
outcome `failure`. A user who cannot be loaded is refused. A user the password
sign-in lets in without a second factor still signs in with the link.

There is nothing to do after upgrading: the check runs whenever a link is
followed, including a link sent before the upgrade.

## Impact

An attacker who can read a user's email signs in as that user, without the
password and past the second factor the password sign-in would have asked for.
They start a sign-in at any application that signs in through OpenIDX, or at
the admin console, choose **Email me a sign-in link**, give the user's address
and follow the link that arrives in the user's mailbox. They are then signed in
to that application with the user's roles.

The accounts a second factor protects are most often administrators'. An
administrator's own TOTP, or a policy that covers administrators, was bypassed
by anyone with access to that administrator's mailbox.

A link is single-use, expires 15 minutes after it is sent unless the expiry was
changed, and is retired when a new one is asked for. None of that limits the
attacker, who asks for the link when they are ready to follow it.

## Workarounds

These are written for v1.36.0, the supported release.

1. **Turn sign-in links off.** On **Security & MFA → Passwordless**, switch
   **Magic Links** off, or send `PATCH /api/v1/identity/passwordless/settings`
   with `{"magic_link_enabled": false}` as an administrator. Since v1.35.0 no
   link is created while it is off, for any user. The sign-in page still offers
   the link and still says it was sent, so tell your users it has gone.

2. **Retire the links already sent.** The switch is read when a link is
   created, not when one is followed, so a link sent before you turned it off
   works until it expires. To retire them at once, use `psql` as the role that
   owns the schema; `app.bypass_rls` lets the statement see every tenant's
   rows.

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    UPDATE magic_links SET status = 'expired' WHERE status = 'pending';
    COMMIT;
    ```

3. **Where links must stay on, take administrators off them.** An
   administrator can turn sign-in links off for their own account: read
   `GET /api/v1/identity/passwordless/preferences`, and send the same body back
   with `PUT` and `"magic_link_enabled": false`. The `PUT` replaces every
   preference, so keep the others as read. No link is created for an account
   with it off. The route needs an administrator's role and acts on the caller's
   own account, so it cannot be set for other users.

4. **Check whether a link was used.** oauth-service logs each sign-in by link
   as an audit event with the action `magic_link_login`, and from v1.34.0 it is
   also stored in the audit log:

    ```sql
    BEGIN;
    SET LOCAL app.bypass_rls = 'on';
    SELECT timestamp, actor_id AS user_id, actor_ip
      FROM audit_events
     WHERE action = 'magic_link_login' AND outcome = 'success'
     ORDER BY timestamp DESC;
    COMMIT;
    ```

    Check the users it lists against **MFA Management → User MFA Status** and
    your MFA policies. A user with TOTP enrolled, or one an enabled policy
    covers, who signed in by link did so without a second factor.

## How to verify the fix

- **The test.** `TestMagicLinkSignsInOnlyWhoNeedsNoSecondFactor`, in
  `internal/oauth` (`magic_link_mfa_testdb_test.go`, added by #1007), follows
  sign-in links through `GET /oauth/magic-link-verify` against a migrated
  database, from both sides. A user with no factor signs in. A user with TOTP
  goes back to the sign-in page with the same pending request, and no
  authorization code is minted. A user whose only factor is email OTP signs in
  with no policy on and goes back with one on. After a policy's grace period
  the link is refused, and a refused link is spent. Run
  `go test ./internal/oauth -run TestMagicLinkSignsInOnlyWhoNeedsNoSecondFactor`
  with Docker available, or with `OPENIDX_TEST_DATABASE_URL` pointing at a
  throwaway database: the test drops and recreates its `public` schema.

- **On a running install.** With sign-in links on, take a test user who has
  TOTP enrolled. Start a sign-in to the console, choose **Email me a sign-in
  link**, give the user's address and follow the link from their mailbox. A
  fixed version returns to the sign-in page and says: "Your account needs a
  second factor, and a sign-in link cannot ask for one. Sign in with your
  password." An affected version signs the user in. A test user with no factor
  enrolled, whom no MFA policy covers, signs in with the link on both.
